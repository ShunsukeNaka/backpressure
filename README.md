# 分散バックプレッシャー伝播 — 最小プロトタイプ

サービス間通信で、レスポンスに載せた単一の `X-Load` ヘッダーだけを頼りに、
呼び出し元が AIMD（Additive Increase / Multiplicative Decrease）で
送信レートを自動調整する、という発想を最小構成で確認するためのコードです。

## 動作確認

このサンドボックス環境には Go がインストールされておらず、ネットワークも
無効なため、コンパイル・実行の確認はできていません。標準ライブラリのみを
使っているので動くはずですが、手元の環境で一度動作確認してください。

## 構成

```
cmd/server/main.go   同時実行数から負荷率を計算し、X-Load ヘッダーで返すだけのサーバー
cmd/client/main.go   X-Load を見ながら AIMD でリクエストレートを調整するクライアント
```

サーバーは「同時に処理できるリクエスト数」に上限（capacity = 20）を設けていて、
それを超えるほど：
- 負荷率 `X-Load` が 1.0 に近づく
- 処理そのものも遅くなる（現実のサービスの劣化を模擬）
- 上限を超えると 503 を返す

## 実行方法

ターミナルを2つ開いて実行します。

```bash
# ターミナル1: サーバー起動
cd backpressure-demo
go run ./cmd/server

# ターミナル2: クライアント起動（AIMDあり）
cd backpressure-demo
go run ./cmd/client
```

出力例（イメージ）:

```
time_s  rate    avg_load        ok      fail
0       1.0     0.05    1       0
1       2.0     0.08    2       0
...
8       32.0    0.85    30      2
9       16.0    0.62    16      0
10      17.0    0.55    17      0
```

負荷が上がるとレートが急減し、落ち着くとまた緩やかに増える、という
AIMDの挙動が `rate` 列に出るはずです。

## 比較: バックプレッシャーなし（naive モード）

同じサーバーに対して、レートを調整せず固定レートで送り続けた場合との比較:

```bash
go run ./cmd/client -naive -fixed-rate=15
```

`fail`（503やタイムアウト）の数が AIMD ありのケースより明らかに増えるはずです。
これが「バックプレッシャー伝播があると過負荷を防げる」ことの最小限の実証になります。

## 次にやれること

- サーバー側に「クライアントとは無関係な背景負荷」を追加して、より現実的な状況にする
- 複数クライアントを同時に走らせて、負荷が全体で均される様子を見る
- `X-Load` を単一指標ではなく複数指標にしてみる
- サーバーを2段構成（A → B → C）にして、多段伝播を試す
